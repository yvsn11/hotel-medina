# Deployment guide (free-tier path)

This guide deploys Hotel Medina with three providers: Neon (PostgreSQL), Render (API) and Vercel (frontend). Render and Vercel redeploy automatically on every push to `main` once the repository is connected; there is no custom deploy workflow and the repo holds no deploy secrets. The CI workflow in `.github/workflows/ci.yml` only builds and tests.

Plans, quotas and sleep behaviour change over time. Check each provider's current pricing page before you rely on a free tier:

- Neon: https://neon.com/pricing
- Render: https://render.com/pricing
- Vercel: https://vercel.com/pricing

Nothing here has been run against live accounts by the authors of this document; treat each step as a checklist and verify against the provider's current UI.

## 0. Prerequisites

- The repository pushed to GitHub, with CI green on `main`.
- Accounts on Neon, Render and Vercel (all can sign in with GitHub).

## 1. Database: Neon

1. Create a project in Neon (PostgreSQL 15 or newer) and a database, for example `medina`.
2. Copy the connection string from the dashboard. It looks like `postgresql://user:password@ep-xxx.region.aws.neon.tech/medina?sslmode=require`.
3. Keep the string as is. The API accepts plain `postgresql://` and `postgres://` URLs and normalizes them to the psycopg 3 driver.
4. You do not need to create any extension by hand. The first Alembic migration runs `CREATE EXTENSION IF NOT EXISTS btree_gist`, which the exclusion constraints need. Neon's extension list includes `btree_gist` (checked at https://neon.com/docs/extensions/pg-extensions); verify it is still listed for your Postgres version. The role in the default connection string is allowed to create it; if the migration reports a permission error, enable the extension from the Neon SQL editor and re-run the deploy.

## 2. API: Render

The blueprint `render.yaml` at the repo root describes the service.

1. In Render, choose New, then Blueprint, and select the repository. Render reads `render.yaml` and proposes a web service `hotel-medina-api` built from `backend/Dockerfile`.
2. Fill the variables marked `sync: false`:
   - `DATABASE_URL`: the Neon connection string from step 1.
   - `CORS_ORIGINS`: your frontend origin(s), comma-separated, no trailing slash, for example `https://<your-app>.vercel.app`. You can set a placeholder now and update it after step 3.
   - `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`: leave empty to use the mock payment provider (the blueprint sets `PAYMENT_PROVIDER=mock`). See step 6 for Stripe.
3. `JWT_SECRET` is generated by Render (`generateValue: true`). Read it from the service's Environment tab if you need it.
4. Deploy. The `preDeployCommand` runs `flask --app wsgi db upgrade && flask --app wsgi seed` before each new version goes live. Both are idempotent, so repeated deploys are safe. If your Render plan does not support pre-deploy commands, open a Render Shell on the service and run the same two commands once, and after every release that adds a migration.
5. Render uses `/api/health` as the health check. The endpoint also checks the database connection, so a wrong `DATABASE_URL` shows up as a failing deploy.

Note on the seed: it creates the public demo accounts (`guest@demo.test`, `staff@demo.test`, password `demo1234`). That is intended for a demo. If you run a real instance, remove `flask --app wsgi seed` from `preDeployCommand` and change or delete those accounts.

## 3. Frontend: Vercel

1. In Vercel, import the repository.
2. Set Root Directory to `frontend`. Vercel detects Vite; the build command is `npm run build` and the output directory is `dist`.
3. Add the environment variable `VITE_API_URL` set to the API origin, for example `https://<your-api>.onrender.com` (no trailing slash). Optionally add `VITE_STRIPE_PUBLISHABLE_KEY` (`pk_test_...`); leave it empty for the mock payment flow.
4. Deploy. `frontend/vercel.json` rewrites every path to `index.html` (so deep links such as `/bookings` work) and sets security headers.
5. Vite inlines `VITE_*` values at build time. After changing one, trigger a redeploy.
6. Go back to Render and set `CORS_ORIGINS` to the final Vercel URL, then redeploy the API.

## 4. Optional: custom domain

Using `app.` for the frontend and `api.` for the API:

| Host | Type | Value | Where to add the domain |
|---|---|---|---|
| `app.example.com` | CNAME | the target Vercel shows for your project (Vercel displays the exact record to create) | Vercel project, Settings, Domains |
| `api.example.com` | CNAME | `<your-service>.onrender.com` | Render service, Settings, Custom Domains |

Both providers issue TLS certificates after DNS propagates. Then:

- update `CORS_ORIGINS` on Render to `https://app.example.com`;
- update `VITE_API_URL` on Vercel to `https://api.example.com` and redeploy the frontend;
- update the Stripe webhook URL if you configured one.

## 5. Cold starts

Free tiers commonly stop idle services and start them again on the next request, and some databases scale to zero when idle. Expect the first request after a quiet period to be slow (the README warns visitors of roughly 30 seconds; the real delay depends on the provider and may differ). A failed first request is usually a timeout, and a retry works. Check each provider's documentation for its current idle behaviour.

## 6. Stripe test mode (optional)

Without Stripe keys the app uses the mock provider and everything works. To use real Stripe test mode:

1. In the Stripe dashboard, switch to test mode and copy the secret key (`sk_test_...`) and publishable key (`pk_test_...`).
2. Create a webhook endpoint (Developers, Webhooks) with URL `https://<your-api>/api/payments/webhook` and select the events `payment_intent.succeeded` and `payment_intent.payment_failed`.
3. Copy the endpoint's signing secret (`whsec_...`).
4. On Render set `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`, and set `PAYMENT_PROVIDER` to `stripe` (it defaults to `stripe` when a secret key is present, but being explicit avoids surprises). Redeploy.
5. On Vercel set `VITE_STRIPE_PUBLISHABLE_KEY` and redeploy the frontend.
6. Pay with test card `4242 4242 4242 4242`, any future expiry, any CVC. A booking becomes `CONFIRMED` only when the webhook arrives (see [ADR-004](adr/004-payment-webhooks.md)), so a wrong webhook secret or URL leaves bookings `PENDING` until the hold expires.

For local testing you can forward events with the Stripe CLI (`stripe listen --forward-to localhost:5000/api/payments/webhook`), which prints its own `whsec_...` secret.

## 7. Verify the deploy

1. Open `https://<your-api>/api/health`. Expect `{"status": "ok"}`.
2. Open `https://<your-api>/api/docs` for the OpenAPI UI.
3. Open the frontend, sign in as `guest@demo.test` / `demo1234` (or `staff@demo.test` / `demo1234` for the back office), search for dates, and book a room.
4. If the browser shows CORS errors, `CORS_ORIGINS` does not exactly match the frontend origin (scheme, host, no trailing slash).
5. Expired holds are released lazily on search and booking. To release them on a schedule, run `flask --app wsgi expire-holds` from a cron job (for example a Render cron job using the same image, or any external scheduler that can reach a shell).

## 8. Rotating JWT_SECRET

JWTs are signed with `JWT_SECRET`, so changing it invalidates every issued token and signs all users out (tokens last 60 minutes anyway).

1. Generate a new value: `python -c "import secrets; print(secrets.token_urlsafe(48))"`. On Render you can also delete the variable and re-add it with a generated value.
2. Set it on the Render service's Environment tab and save; Render redeploys.
3. Users sign in again. There is no overlap window: the API holds a single secret.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Deploy fails at pre-deploy | Wrong `DATABASE_URL`, or `btree_gist` could not be created (see step 1) |
| Health check fails | Database unreachable; check the Neon connection string and that the project is not suspended |
| Browser CORS error | `CORS_ORIGINS` mismatch |
| Frontend calls `localhost` or its own origin | `VITE_API_URL` missing at build time; set it and redeploy |
| Booking stays `PENDING` after payment | Webhook not delivered or `STRIPE_WEBHOOK_SECRET` wrong; check Stripe's webhook delivery log |
